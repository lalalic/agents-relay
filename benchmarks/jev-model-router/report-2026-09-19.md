# Jev model-router benchmark report — 2026-09-19

## Scope

Evaluate Cloudflare Workers AI `typesafe/jev` as a typed semantic decision layer for model-router decisions without changing production routing.

The benchmark keeps deterministic eligibility fixed. Provider/model availability, required capabilities, tool/context/modality fit, privacy, explicit user constraints, and known quota/health conditions remain hard policy. Jev is tested only on semantic route-tier selection among eligible choices.

## Cloudflare / Jev API

Cloudflare documents Jev as `typesafe/jev`, a third-party structured evaluation model with a 32K context window. One request supplies a shared `state` plus typed questions:

- `choice`: selects one criterion and returns `choice`, `confidence`, and per-option probabilities.
- `score`: places the state on an ordered scale and returns a numeric score, confidence, legend, and probabilities.
- `noul`: returns a calibrated yes/no probability in `noul`.

The documented response also reports model version and input/output token usage. Cloudflare's example currently reports model version `jev-1.13.0`.

Workers AI REST endpoint:

`POST https://api.cloudflare.com/client/v4/accounts/{account_id}/ai/run`

Request envelope:

```json
{
  "model": "typesafe/jev",
  "input": {
    "state": {},
    "questions": {}
  }
}
```

Authentication requires a Cloudflare account ID plus an API token with Workers AI Read and Workers AI Edit permissions.

Sources:

## Fixtures

The benchmark contains 13 real durable task inputs extracted from Agents Relay PR task markers:

- PR #23: Jev model-router benchmark.
- PR #9: registry scope, CLI surface, routing policy, registered-agent dispatch, evidence loop, capability scoring, end-to-end dogfood, and final objective review.
- PR #29: P0 idempotent job/task reliability repair.
- PR #28: workspace-wide repository watching.
- PR #27: targeted adapter capability-gate removal.
- PR #26: dashboard job-list/root-cause repair.

Each fixture records the current durable routing decision normalized to one of four semantic tiers and an independently assigned strong-reasoning reference tier.

The normalization deliberately avoids provider selection. Jev is not allowed to choose an unavailable provider or override model-router hard gates.

## Current-router comparison

Fixture count: **13**

Current semantic tier == strong-reasoning reference: **6 / 13 = 46.2%**

Durable tasks in `SUCCEEDED` state: **9**

Among succeeded tasks, current tier == strong-reasoning reference: **4 / 9 = 44.4%**

This is not evidence that the current router achieves only 44–46% quality. The reference labels are judgment labels, and task terminal state is a weak downstream proxy affected by implementation quality, transport, retries, cancellation, and test coverage. The main value is identifying disagreement cases for replay.

Notable disagreement patterns in this fixture set:

- several cross-cutting security/architecture/evaluation tasks were routed to a balanced medium tier while the strong-reasoning reference prefers high reasoning;
- the P0 idempotency repair and workspace-wide watch were routed to the fast tier while the reference prefers balanced medium;
- the small, targeted capability-gate removal agrees on the fast tier;
- broad end-to-end verification and final objective review agree on high reasoning.

## Strong reasoning-model baseline

The 13 reference route labels were independently re-reviewed with GPT-5.6 Sol on 2026-09-19 using only each fixture's task, requirements, risk, and deterministic eligible-route set. The review agreed with all 13 stored reference labels. This gives the fixture baseline explicit model provenance while keeping it separate from the current durable router decision.

The baseline remains a judgment reference rather than ground truth. It is useful for replay disagreement analysis, not as a claim that one semantic tier is universally optimal.

## Benchmark runner

`run.mjs` asks three typed questions in one Jev request per fixture:

1. **Choice** — choose the best eligible semantic route tier.
2. **Score** — rate required reasoning depth from narrow/routine through very high.
3. **Noul** — estimate whether the routing decision should be escalated to a strong reasoning-model fallback.

It records:

- Jev choice vs strong-reasoning reference;
- Jev choice vs current router;
- multiclass Brier score from Choice probabilities;
- fallback rate using Choice confidence and Noul probability;
- p50/p95 REST latency;
- input/output tokens;
- model version;
- failures.

Default fallback threshold `0.75` is benchmark-only and must not become production policy without calibration.

Cloudflare's public Jev model page points pricing to the account dashboard instead of publishing a Jev-specific token price. The benchmark therefore records token usage and leaves dollar cost unset rather than inferring a price from unrelated models.

## Integration recommendation

**Production routing: no change.**

Jev is architecturally suitable for a narrow experiment because its typed Choice/Score/Noul outputs match the routing problem and provide probabilities useful for calibration. But there is not yet live empirical evidence from this Cloudflare account.

If a live run validates quality, calibration, and latency, the integration boundary should remain:

`deterministic eligibility -> Jev semantic tier -> confidence/fallback gate -> model-router maps tier to currently eligible profile`

Jev should not own:

- provider/model discovery;
- hard capability/privacy/security/quota gates;
- direct executor selection outside the eligible set;
- production routing when its response is malformed/unavailable;
- final decisions for ambiguous/high-risk cases below a calibrated confidence threshold.

The next benchmark run should use at least 3 repetitions per fixture to make p50/p95 less brittle. Review disagreement cases manually before selecting a confidence threshold. Production enablement should remain off until Cloudflare billing/credits are available and the live report includes acceptable false-route behavior, calibration, fallback rate, latency, and observed account cost.
