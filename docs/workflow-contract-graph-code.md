# Workflow Contract → Graph → Code traceability

## Authority

- Contract owns event names, schemas, event producer/owner, action/condition interfaces, permission, and invariants.
- Canonical executable `workflow/*.mmd` files own transitions and guard/action sequencing.
- Code implements observed conditions and controlled effects; it may not introduce another transition policy.
- SQLite is authoritative for executions, generations, routing and observed outcomes.
- `workflow/main.mmd` is **presentation/navigation only**. It is never loaded as an executable graph.
- A review change request is a normal fix loop; a platform failure enters the existing guarded recovery graph, and unknown external outcomes require reconciliation, never blind re-execution.

## Current incremental implementation

- `src/workflow/usage-index.ts`: `executableGraphs` loads the strict Graph V2 subset, excluding the presentation entry; `buildWorkflowUsageIndex` derives reverse source references for event/request/guard/action/state/emit symbols with graph and line.
- `whereWorkflowSymbol` is read-only and deterministic, suitable for a future `workflow where` CLI without duplicating a maintained registry.
- Existing `src/workflow/graph-v2.ts` parses and validates topology and guards/actions/events; `src/workflow/definitions-v2.ts` binds current typed graphs to the existing registries.
- Existing `src/workflow/contracts.ts` contains the canonical event/action symbol inventory. Schema/ownership/permissions are not yet complete for every symbol; avoid inferring those from the index.

## Follow-on gates (not yet implemented)

1. Contract metadata: stable typed symbol IDs with schema, owner, permissions and invariants. Validate generated registries against the canonical contract and graph; do not add hand-maintained parallel symbol maps.
2. Shared Condition Registry: read-only facts/conditions usable before actions as guards and after actions as effect verification. Return `Verified | Failed | Unknown`; `Unknown` must reconcile and not retry an external side effect.
3. Graph-controlled authorized Action requests, generation/lease fencing, execution ID correlation and postcondition trace recording. Reject arbitrary CLI force-terminalization.
4. CLI read-only `discover / inspect / where / evaluate` plus guarded `action request`; all entry points share the same graph runtime.
5. L1 per-wire contract tests (ownership, orphan symbols, reachability, terminal objective gate, no duplicate control path), L2 durable/runtime tests and Thread B's independently owned L3 corpus.

Do not merge this exploratory graph/index baseline as a claim of complete refactoring until the remaining gates pass review.

## Entry Graph legend and CLI Action audit (2026-10-20)

`workflow/main.mmd` is the non-executable conceptual entry. Its `contract:`, `graph:`, `code:`, `state:` and `guard:` labels are documentation/navigation, not callable action identifiers. Executable child Graph nodes use canonical `state:`, `guard:` and `action:` semantic IDs. An `action:` may internally invoke an `effect.*` side effect; this does not authorize arbitrary CLI execution.

`agents-relay workflow actions` derives the **48 distinct executable action IDs** and their `graphReferences` from all executable Graph files. Each entry's `cli` value explicitly says **inspect-only**. `workflow discover`, `inspect`, `where`, `evaluate`, `verify` and `trace` are read-only; the six routed `workflow action --action task.{retry,recover,cancel,unblock,escalate,resume-troubleshooter}` controls delegate to existing guarded Task command semantics. Those six control identifiers do **not** constitute implementations of the 48 internal Action IDs. Direct CLI execution of all 48 is **not implemented/approved**; exposing it would require a shared durable Graph-authorized request protocol with event/schema/owner/permission, state/guard checks, generation/lease fencing, and postcondition evidence, including unknown-outcome reconciliation. Do not claim CLI coverage from the read-only catalog.

### CLI L3 coverage gate

`test/verification/l3-cli-actions.test.mjs` runs the real compiled CLI as a subprocess with isolated storage. It discovers and resolves all 48 Graph Action IDs, verifies the real SQLite action ledger trace for a reserved launch attempt, and confirms each of the 48 internal actions is **rejected** as an unsafe direct CLI mutation without a Graph-authorized Task control. The ledger is checked unchanged. This is **CLI inventory + negative/fail-closed L3 evidence, not a positive effect-execution test**. In particular, **0/48 direct CLI Action positive executions are verified**; these paths remain **NOT_RUN**, and exposing them requires Graph-selected event requests and durable authority/guard/execution evidence. Existing runtime action/recovery tests do not establish that a direct CLI caller can safely execute those internal actions.

### Follow-up CLI/Graph L3 execution evidence

The six explicitly allowed `workflow action --action task.*` Task controls now have **positive isolated L3** through the compiled CLI subprocess, a real single-Job HTTP service, the same daemon-owned control handler, the owning Graph/Task action implementation, and authoritative SQLite reload: `task.cancel`, `task.retry`, `task.unblock`, `task.recover`, `task.escalate`, and `task.resume-troubleshooter`. This is exercised by `test/verification/l3-cli-actions.test.mjs` (also registered in `npm run test:verification:l3`). It includes unauthorized cross-Job and unsupported-control rejection (HTTP 409), repeated cancel rejection, duplicate human response rejection, and no false human-delivery receipt or terminal Objective. In the legacy Orchestrator fixtures, successful retry/unblock/recover requests can be subsequently placed back into `BLOCKED` by the execution router; that is not a verified Worker launch.

The 48 internal `action:` IDs remain callable **only by their owning production Graph runtime**, not as arbitrary direct CLI mutations. Their CLI inventory and all 48 direct-execution rejection paths are tested; **positive standalone CLI execution for these 48 IDs remains NOT_RUN**. The runtime Action implementations must not be exposed as unconditional commands just to increase test coverage. A future CLI event-request protocol must bind authoritative Graph state, guards, identity/owner/permissions, current generation/lease and durable postconditions before any new external mutating action entry point is considered supported.
